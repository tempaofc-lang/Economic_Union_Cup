# Prompt 设计与拼音解译链路

> 📌 **定位**：本篇是实现层文档，描述**已经提交并测试通过的代码**（`agent.py` v3.0 + `pinyin_codec.py`）。
> 输出字段与 `/api/agent` 契约以 [05 §3.3](05_B组详细分工与项目框架.md) 为准 —— 本模块已对齐。

> 对应代码：`手语识别系统/agent.py`（v3.0）、`手语识别系统/pinyin_codec.py`、`手语识别系统/vocab.json`
> 版本：2026-10-22 晚（v3：把解码交给 LLM）｜ 作者：古宇轩

---

## 1. 为什么要再改一次

v2 的链路是「**本地查表解码 → LLM 组句**」：拼音先经过 `pinyin_codec` 的 17 词封闭词表做精确/别名/编辑距离匹配，
匹配不上就丢弃，然后再把中文词交给 LLM 连成句子。

问题在评审视角下一看就穿：

> **真正的难点是"拼音 → 词"，而这一步是查表算法做的，LLM 只是把已经解好的词排个序。**
> 换个说法：这不是"LLM 解译"，是"查表 + 润色"。

具体后果：

| 输入 | v2 的结果 | 问题 |
| :-- | :-- | :-- |
| `shenfenzeng`（少一个 h） | 侥幸被编辑距离救回 | 靠运气，阈值一调就废 |
| `wo yao buban` | `wo` / `yao` 直接被丢弃 | LLM 根本没看见，也就谈不上理解 |
| `shen fen zheng`（分写） | 依赖归一化规则 | 规则一多就难维护 |

所以 v3 把顺序倒过来：**原始拼音直接交给 LLM 解码**，本地查表的角色从"闸门"降级为"交叉校验"。

## 2. v3 的链路

```
YOLO 拼音  ["wo","yao","buban","shenfenzeng","tiyuguan"]
   │
   ├─► 本地查表（pinyin_codec）── 并行跑一遍，只用于交叉校验，不拦数据
   │       结果：["补办","身份证"]
   │
   ▼
LLM（DeepSeek，流式）── 逐 token 判断：词表命中 / 推断 / 噪声
   │       结果：[我(inferred), 要(inferred), 补办(vocab), 身份证(inferred), tiyuguan(ignored)]
   ▼
成句 + 导办回答 + 办事卡片 + 主动反问
   │
   ▼
交叉校验：LLM 结果 vs 本地查表 → 一致 / 不一致，界面逐行标出来
```

实测同一串 `wo yao buban shenfenzeng tiyuguan`：

| 策略 | 解码出的词 | 译文 |
| :-- | :-- | :-- |
| `local`（旧行为） | `补办`、`身份证` | 您好，我想补办身份证，请问需要准备什么材料、去哪个窗口办理？ |
| `llm`（默认） | `我`、`要`、`补办`、`身份证` | 您好，**我要**补办身份证，请问需要带什么材料、去哪个窗口？ |

差异不只是多了两个字——`local` 丢掉的是**说话人的意图（"我要…"）**，只剩业务名词，读起来像工单而不是一个人在说话。

## 3. 三条护栏：让 LLM 解码不放飞

把解码权交给大模型，风险是它开始编。用三件事兜住：

### 护栏一：每个拼音必须交代来源

输出里 `tokens[]` 强制覆盖输入的**每一个**拼音，每个都带 `source`：

- `vocab` —— 与词表吻合
- `inferred` —— 推断（错拼纠正、词表外常用词），**必须在 `note` 里写依据**
- `ignored` —— 判为噪声

界面上逐行显示「来源」徽章和推断理由。评委问"这个'我'哪来的"，可以直接指着说
"模型标了 inferred，理由是第一人称代词、词表外、结合语境推断"——**有痕迹，就不是玄学**。

### 护栏二：本地查表做交叉校验

本地查表照跑，结果写进 `mapping.local_word`，与 LLM 的判断并排显示：

- 两边都有词且相同 → `✓`
- 两边都有词但不同 → `✗ 不一致`（这种行要重点看，可能是模型编了，也可能是本地表漏了）
- 一边没有词 → `—`（无法比较，不误报为冲突）

这一步还顺便产出了答辩素材：「本地查表命中率 vs LLM 解译覆盖率」的对比。

### 护栏三：政务数字不归 LLM 管

窗口号、材料、费用由 `data/gov_kb.json` 提供，通过 `query_gov_kb` 工具注入，
**办事卡片以知识库为准覆盖模型输出**。模型只负责措辞。

## 4. System Prompt 逐段设计

完整 prompt 在 `agent.py` 的 `SYSTEM_PROMPT_TEMPLATE`，用占位符 `__VOCAB_LINES__` 注入词表
（不用 `str.format()`，避免 JSON 里的花括号要写成 `{{ }}` 这种坑）。

### 4.1 第一段：把"理解"而不是"查表"钉死

```
你的任务是**判断这串拼音想表达什么政务诉求**，而不是去词表里做查表匹配。
词表只是参考基线；查表是备用手段，不是目的。
```

这是整份 prompt 最重要的一句。v2 的写法是"你只能在这 17 个词的范围里工作"，
那句话直接把模型锁成了查表机。

### 4.2 第二段：把缺陷讲透

列出六类真实故障：无声调、拼写错误（含 `n/l`、`zh/z`、前后鼻音）、连写分写不统一、手语语序、重复、噪声。
并给了一个具体例子：`shenfenzeng` 很可能是 `shenfenzheng`。

不写这段，模型会把 `buban buban buban` 理解成"要补办三次"。

后面紧跟一句 **"你自己纠正，不要向用户抱怨"** —— 否则它可能输出"您输入的拼音格式有误"，
那对听障群众是灾难。

### 4.3 第三段：词表作为"参考基线"而不是边界

```
- 拼音与表中某一项吻合 → source 标 "vocab"
- 不在表里但能在政务语境下合理推断 → source 标 "inferred"，并在 note 写清依据
  允许你推断，但必须留下痕迹，不要假装它是词表命中的
- 明显是噪声 → source 标 "ignored"
- queren 是控制信号，触发成句但不参与语义
```

关键是把权限和代价讲清楚：**可以推断，但必须标注**。这样"模糊匹配"才既敢做又可审计。

### 4.4 第四段：成句与导办的约束

- 可以补"我""请问"这类衔接词，但**严禁补充原词里没有的业务事项**。
- 导办必须给具体窗口 + 具体材料；不确定的费用不写。
- **answer ≤ 80 字**：这句要 21px 大字显示在群众屏幕上，超过两行就不看不完了。

实测加了 80 字约束后，回答从 200+ 字压到 60 字左右，信息密度反而更高。

### 4.5 第五段：强制 JSON + 七个键

`tokens` / `words` / `translation` / `answer` / `confirm_card` / `clarify` / `confidence`。

配合 `response_format={"type":"json_object"}`。DeepSeek 的 JSON 模式有两条硬要求，这里都满足：
prompt 里出现 "json" 字样、给出期望输出的样例。

### 4.6 第六段：三个示例，每个对准一类故障

| 示例 | 输入 | 考什么 |
| :-- | :-- | :-- |
| 1 | `nihao shenfenzheng diushi buban buban` | 重复去重 + 控制信号 |
| 2 | `shenfenzeng diushi le buban` | **错拼纠正 + 词表外推断（le → 了）** |
| 3 | `chuangkou tiyuguan` | 噪声丢弃 + 泛词触发反问 |

示例 2 是这次新加的，也是最能说明"LLM 在真的理解"的一条。

## 5. 流式实时输出

### 5.1 为什么要关掉思考模式

实测同一段输入：

| 配置 | 首 token | 总耗时 |
| :-- | --: | --: |
| JSON + 思考模式默认 | 2572 ms | 2621 ms |
| **JSON + `thinking: disabled`** | **787 ms** | **1126 ms** |

首 token 快 3 倍。这个任务（拼音映射 + 造句）不需要长链推理，关掉思考几乎不损失质量，
但演示时的"实时感"差别巨大。用环境变量 `LLM_THINKING=1` 可以随时打开对比。

### 5.2 SSE 事件设计

`POST /api/agent/stream` 推四种事件：

| 事件 | 时机 | 前端做什么 |
| :-- | :-- | :-- |
| `meta` | 立即（本地查表 + 知识库都完成，约 10~20ms） | 先渲染输入侧：token、词表命中、工具轨迹 |
| `delta` | 模型每吐出一块 | 从流式 JSON 里正则抠出 `translation` 当前值，做成打字机效果 |
| `error` | 出错 | 提示并继续等 final |
| `final` | 结束 | 用结构化结果整体替换（确保以最终值为准） |

前端边收边渲染的做法：模型输出的是 JSON 文本，用
`/"translation"\s*:\s*"((?:[^"\\]|\\.)*)/` 抠出**尚未闭合**的字符串值，先显示再说。
`final` 到达后用权威数据覆盖，避免半截文本留在屏幕上。

### 5.3 实测时间线

```
meta   +  12 ms   本地解码=['身份证','丢失','补办']，工具 query_gov_kb ✓
delta  +1092 ms   首块文本到达，开始渲染大字翻译
final  +1839 ms   结构化结果补齐卡片/反问/明细
```

也就是说：**12ms 就有反馈，1.1 秒开始出字，整个答复 1.8 秒完成**。
对比非流式，用户要干等 2 秒才看到任何东西。

## 6. 两种策略

请求体里的 `strategy` 字段：

| 值 | 行为 | 用在哪 |
| :-- | :-- | :-- |
| `llm`（默认） | 原始拼音交给 LLM 解码，可纠错、可推断 | 正式演示 |
| `local` | 只把词表过滤后的**中文词**给 LLM，不给原始拼音 | 对照组，用来说明"为什么必须有 LLM 解码" |

`local` 的实现细节值得注意：它**不把原始拼音传给模型**。一开始我偷懒只改了措辞，
结果模型照样把 `wo` 推断成"我"，两种策略输出完全一样——对照组就失去意义了。
真正有效的对比必须切断信息源。

## 7. 参数与成本

| 参数 | 取值 | 理由 |
| :-- | :-: | :-- |
| `temperature` | 0.2 | 政务场景要稳定复现 |
| `max_tokens` | 700 | 输出含 7 个字段 + tokens 数组，留足余量防截断 |
| `timeout` | 30s | 超时回退规则引擎，界面不能卡死 |
| 重试 | 1 次 | JSON 模式偶发空返回 |
| 思考模式 | 关 | 见 §5.1 |
| 缓存 | 非流式开启 | 流式故意不缓存，避免"看起来实时其实命中缓存" |

单次调用约 1.5k~2k tokens（prompt 里词表和示例占大头）。整场演示几十次调用是分钱级别。

## 8. 兜底与容错

```
① LLM 流式成功 → source="llm"
② 流式失败（网络/额度/超时/JSON 解析失败）
   → 退回非流式再试 1 次 → 仍失败则
③ 本地规则引擎 → source="rule"，error 字段记录原因
```

宽容解析覆盖的脏数据：

- ` ```json ` 围栏包裹 → 剥掉
- `confidence` 为 `null` / `"95%"` / `"0.9（较高）"` → 宽容转数值
- `answer` 自带 `【政务导办回答】` 前缀 → 剥掉后由代码统一添加
- `tokens` 缺失或为空 → 回退到 `words` 字段，再回退到本地查表结果

## 9. 一个踩过的坑：`.env` 静默加载失败

`load_dotenv()` 依赖调用栈和当前工作目录。当 uvicorn 从 `backend/` 启动、
又用的是另一个 Python 环境时，它可能**找不到 `手语识别系统/.env`，而且不报错**——
表现就是"LLM 不可用"，但代码看起来完全正常。

现在改成按固定候选路径显式解析（自带极简 `.env` 解析器，不依赖 python-dotenv），
并在 `/api/health` 返回 `env_file` 和 `api_key_present` 两个字段。
以后遇到"LLM 突然不可用"，先看这两个字段，不用猜。

同类问题还有一个：`--reload` 默认只监听启动目录，而 `agent.py` 在 `手语识别系统/` 下，
改了不会热重载，看起来像"改了没生效"。`run_dev.ps1` 现在显式加了 `--reload-dir`。

## 10. 已知限制 / 下一步

1. **`tokens` 覆盖度靠 prompt 约束**，没有硬校验。可以在 `_normalize_tokens` 里比对
   输入 token 数量，缺了就用本地结果补并标注——下一步做。
2. **交叉校验只做"是否一致"**，没有量化"谁的准确率高"。等 A 组给标注数据后
   可以算出两套解码的 precision，写进技术文档。
3. **推断词没有经过人工确认**，演示时如果评委追问，按 `note` 里的理由解释即可。
4. **流式在前端用正则抠字段**，属于实用取向的取巧；如果后端愿意多一次调用，
   改成"先流式出纯文本译文，再单独出结构化字段"会更干净，但会多花一次 token。
