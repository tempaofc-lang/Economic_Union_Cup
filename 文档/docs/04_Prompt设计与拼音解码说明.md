# Prompt 设计与拼音解码说明

> 对应代码：`手语识别系统/agent.py`、`手语识别系统/pinyin_codec.py`、`手语识别系统/vocab.json`
> 版本：2026-10-22 ｜ 作者：古宇轩

---

## 1. 为什么这次要重写

数据集受限，A 组的 YOLO 改为输出**无声调拼音**而不是中文词组。表面上只是换个输入格式，实际上把一个简单问题变成了难题：

| | 中文词组（旧） | 无声调拼音（新） |
| :-- | :-- | :-- |
| 输出示例 | `["你好","身份证","补办"]` | `["nihao","shenfenzheng","buban"]` |
| 歧义 | 几乎没有 | **极大**：`shi` 可以是 是/事/十/时/市/识/实…… |
| 谁来做还原 | 不需要 | 必须有人做 |

如果直接把拼音丢给大模型让它"看着办"，后果是：同一个拼音每次可能还原成不同的词，而且它会为了"把句子写通顺"而**编造业务事项**（比如凭空补上"我要预约"）。答辩时评委只要问一句"这个词是从哪来的"，就答不上来。

---

## 2. 于是我们做了两层，而不是一层

```
YOLO 输出        ["nihao", "shenfenzheng", "diushi", "buban", "queren"]
                        │
                        ▼  第一层：pinyin_codec.py（确定性，0 网络，毫秒级）
                 封闭词表解码（17 类，精确 → 别名 → 模糊 → 忽略）
                        │
                        ▼
中文词序列        ["你好", "身份证", "丢失", "补办"]   ＋ confirmed=True
                        │
                        ▼  第二层：agent.py（DeepSeek，一次 API 调用）
                 重排语序 + 补全省略成分 + 生成导办回答
                        │
                        ▼
翻译句 + 导办回答
```

**这样拆的好处：**

1. **可解释**：每个中文词都能追溯到"哪个拼音、用哪条规则匹配的"，答辩时可以逐条演示。
2. **零幻觉风险的第一道闸**：词表外的拼音直接丢弃，大模型拿不到它，也就编不出对应的业务。
3. **省 token**：让模型做 17 选 1 的映射没有价值，它擅长的是"把词连成话"。
4. **可降级**：词表解码不依赖网络，断网时界面仍然能把拼音显示成中文。

> 大模型仍然拿到了**原始拼音**（见 §3.5），所以当拼音不在词表里时，它还有机会补救。

## 3. System Prompt 逐段拆解

完整 prompt 在 `agent.py` 的 `SYSTEM_PROMPT_TEMPLATE` 里。它由六段组成，每段解决一个具体问题：

### 3.1 角色设定

```
你是「手语视界」政务服务大厅的语义解译引擎，服务对象是听障办事群众。
```

**为什么**：不写角色，模型会写成"作为 AI 助手，我理解您想…"这类客服腔，不适合直接显示给群众看。

### 3.2 把输入的缺陷提前告诉它

```
1. 语序不符合汉语习惯——手语常把"话题"放前面、动作放后面
2. 有重复——同一个手势会被连续识别多次
3. 有误识别——偶尔混入无关的孤立词，或少量词表外的拼音
```

**为什么**：这是最容易被忽略、又最有用的一段。不写这三条，模型会把 `buban buban buban` 理解成"要补办三次"，把乱序当成语义。

还特意加了一句「你必须在心里自动纠正，**不要向用户抱怨**」——否则它可能输出"您输入的拼音格式有误，请重新输入"，那对听障群众是灾难。

### 3.3 封闭词表

```
# 二、允许词表（你只能在这 17 个词的范围里工作）
- `nihao` = 你好
- `shenfenzheng` = 身份证
...
```

**为什么**：这是**防止编造的核心手段**。给了明确边界，模型就不会自由联想。

词表是**从 `vocab.json` 动态渲染**的（`_build_vocab_lines()`），改了词表不用改 prompt，避免两处不一致这种经典事故。

### 3.4 三步任务分解

把"解码 → 成句 → 导办"拆成明确的三步，并各自给出约束：

- 第二步约束：**"可以用衔接词，但严禁补充原词里没有的业务事项"**，并给了反例（原词没有"预约"就不能说"我已预约"）。
- 第三步约束：必须包含具体窗口 + 具体材料；**不确定的费用就不写**。

**为什么**：不做约束时，模型倾向于"多写点显得专业"，结果编造出并不存在的窗口号和收费标准 —— 这在政务场景里是硬伤。

另外加了长度约束「**80 字以内**」：这句话要 21px 大字显示在群众屏幕上，超过两行就看不完了。实测加了这条之后，回答从 200+ 字压到了 60 字左右，信息密度反而更高。

### 3.5 输出格式 + JSON 模式

```
只输出一个 json 对象，不要 markdown 代码块，不要任何解释文字。结构严格为：
{"words": [...], "ignored": [...], "translation": "...", "answer": "...",
 "confirm_card": {...} | null, "clarify": {...} | null, "confidence": 0.0}
```

**为什么固定成 JSON**：后面 UI 有 7 个字段要分别使用（大字翻译、导办回答、办事卡片、主动反问、置信度条、被忽略的词），解析字符串比解析 JSON 脆弱得多。

**七个字段的用途**：

| 字段 | 谁在用 | 用途 |
| :-- | :-- | :-- |
| `translation` | 李彤 | 21px 大字翻译（主视觉） |
| `answer` | 李彤 | 政务导办回答 |
| `confirm_card` | 李彤 | 结构化办事卡片：业务名 / 材料清单 / 窗口 / 费用 |
| `clarify` | 李彤 | 词太少时**主动反问** + 2~3 个选项，渲染成大按钮让人点 |
| `confidence` | 李彤 | 置信度条 + "我们知道自己哪不可靠"的答辩证据 |
| `words` | 全员 | 显示"我到底听懂了哪几个词"，可追溯 |
| `ignored` | 全员 | 误识别被丢弃的词，答辩时可解释"为什么没瞎猜" |

> `confirm_card` 与 `clarify` 是对齐团队《B 组详细分工与项目框架》§3.3 的 `/api/agent` 契约预留的。
> 现在 `parse_semantics_detail()` 返回的字典可以直接作为 `/api/agent` 的响应体（再加 `session_id` / `mode` 两个字段即可），
> 将来包一层 FastAPI 时**不需要改解译逻辑**。

**`clarify` 是最值得讲的设计**：识别不准是客观事实，与其硬猜一个业务，不如让 Agent 主动问一句"请问您要办身份证还是社保卡"，
把"我们识别不准"的短板变成"Agent 会主动沟通"的长板。实测输入 `chuangkou`（只有一个词"窗口"）时，模型输出：

```json
{"clarify": {"question": "请问您要办理哪项业务？",
             "options": ["身份证补办", "社保卡激活", "营业执照办理"]},
 "confidence": 0.25}
```

这条行为是**写进 prompt 的硬约束**（"宁可反问，也不要硬猜——猜错比不答更糟"），不是碰运气碰出来的。

代码里配合了 `response_format={"type": "json_object"}`。DeepSeek 的 JSON 模式有两条要求，都在这里满足了：

1. prompt 中必须出现 "json" 字样（本条标题里就有）；
2. 必须给出期望输出的样例（下面第五段就是）。

> ⚠️ DeepSeek 官方文档明确提到：JSON 模式下**有概率返回空 content**。所以代码里做了 3 次重试（`LLM_MAX_RETRIES`），全失败才走规则引擎。

`confidence` 让模型自评忠实度，用途有两个：界面上可以显示成"可信度"，答辩时可以作为"我们知道自己在哪不可靠"的证据。

### 3.6 Few-shot 示例：每个示例对准一种真实故障

| 示例 | 输入 | 考的是什么 |
| :-- | :-- | :-- |
| 1 | `nihao shenfenzheng diushi buban buban` | 重复词去重 |
| 2 | `buban shenfenzheng` | 语序倒置 + 成分缺失 |
| 3 | `qingwen shebaoka jihuo chuangkou nali tiyuguan` | 混入无关词 + 词表外拼音 |
| 4 | `xiexie` | 无法成句时怎么优雅回应 |
| 5 | `chuangkou` | **词太少时主动反问**，而不是硬猜一个业务 |

**为什么是这五类**：它们不是随便挑的，而是我们从 YOLO 的实际输出模式里能预期到的**全部五类故障**。few-shot 的价值不在"给例子"，在于"每个例子修一种病"。

第四条定义了"兜底话术"：`您好，我没能完整表达，请再问我一次。` —— 这句话在听障用户场景里非常重要，它给了对方一个明确的重试信号，而不是一句冷冰冰的"识别失败"。

第五条定义了"不敢猜"的行为：只有"窗口"一个词时，它不会编出"窗口办理"这种空话，而是返回 `clarify` 反问 + 三个具体选项。

### 3.7 最终的用户消息

除了原始拼音，我们还会把**规则引擎的预解码结果**一起发过去：

```
输入拼音：nihao shenfenzheng diushi buban
规则引擎预解码：你好、身份证、丢失、补办
请按 system 指令输出 json。
```

**为什么**：给模型一个"锚点"。锚点正确时它不敢乱跳；锚点缺失（词表外的词）时它还能用原始拼音补救。

## 4. 参数怎么定

| 参数 | 取值 | 理由 |
| :-- | :-: | :-- |
| `temperature` | 0.2 | 政务场景要稳定复现，不要创意。同一段手语每次结果应基本一致 |
| `max_tokens` | 600 | 输出含 5 个字段 + 一段 80 字回答，600 足够且能防止截断 |
| `timeout` | 25s | 超时立刻走规则引擎，界面绝不能卡住等 API |
| 重试次数 | 2 | 应对 JSON 模式偶发空返回 |
| 缓存 | 开启 | 演示时同一段手语会重复触发，缓存避免重复烧钱和重复等待 |

**成本**：单次调用约 1.2k~1.5k tokens（prompt 里词表占大头）。按 flash 模型的价格，整场演示几十次调用是**分钱级别**，不需要担心。

## 5. 三层兜底：保证界面永远有输出

```
① 大模型成功           → source="llm"
② 大模型失败（网络/额度/超时/JSON 解析失败）
   → 再试 2 次 → 仍失败 → ③
③ 本地规则引擎         → source="rule"，error 字段记录失败原因
```

界面无论哪种情况都有话可说，不会白屏。测试脚本里第 11、12 条用例专门验证这条路径。

兜底还覆盖了几种"脏数据"：

- 模型返回 ```json 包裹的内容 → `_parse_json_loose()` 会剥掉围栏
- 模型把 `confidence` 写成 `null` / `"95%"` / `"0.9（较高）"` → `_to_confidence()` 宽容解析
- 模型在 `answer` 里自己加了 `【政务导办回答】` → 统一剥掉后由代码添加，避免双层前缀

## 7. 什么时候该改哪里

| 现象 | 改哪里 |
| :-- | :-- |
| 某个拼音总被忽略 | `vocab.json` 的 `aliases` 加别名 |
| 一句话被拆错、语序不对 | `SYSTEM_PROMPT` 的第二段（输入缺陷）和示例 |
| 回答太长 / 太短 | prompt 里「80 字以内」那个约束 |
| 编造了不存在的窗口或收费 | prompt 第三步的约束 + `test_agent.py` 的 `forbid` 列表 |
| 界面上想显示中文而不是拼音 | 用 `pinyin_codec.to_hanzi(tokens)`（见下） |

> `app.py` 里目前直接显示 `t['word']`。如果 A 组的模型输出拼音，界面上的"识别词序列"就会显示成 `nihao → shenfenzheng`。改成中文只需在 `app.py` 里加一行：
>
> ```python
> from pinyin_codec import to_hanzi
> display_words = to_hanzi([t["word"] for t in _CURRENT_TOKENS])
> ```
>
> 这一步属于前端改动，需要李彤确认后再动，避免与本轮解译层重写冲突。
